```
  ↓
VERIFY
  ↓
DOCUMENT
  ↓

  ↓

```

Do not continue to the next major feature simply because code was generated.

## 42. ONE PRIMARY PHASE PER DEVELOPMENT SESSION

As a default rule:

**Work on one primary phase per development session/day.**

However, this is NOT a strict time limit.

If a phase is complex, especially:

- NLP
- Wellness Prioritization
- Security
- Integration
- Deployment

the phase may take multiple days.

Never rush a technically or clinically sensitive module simply to maintain a one-phase-per-day schedule.

Conversely, if a phase is very small, multiple related phases may be completed in one day if they can be safely verified.

The actual rule is:

> One verified development unit at a time.

## 44. AI CONTEXT PRESERVATION

At the beginning of every new development session, first review the current project state.

The development team may provide:

- Current project folder structure
- DEVELOPMENT_LOG.md
- Relevant source files
- Current database schema
- Current API documentation
- Current error messages

Do NOT assume that the previous session's code is still unchanged.

Before modifying anything:

1. Review the current structure
2. Identify what has already been implemented
3. Identify what has been tested
4. Identify the current phase
5. Identify unresolved issues
6. Identify the next required task

Then continue from the current state.

---

## 45. DO NOT REDISCOVER THE PROJECT

To conserve AI credits and avoid unnecessary work:

DO NOT:

- Rebuild the entire project
- Rewrite working files
- Re-explain the entire architecture every session
- Regenerate existing models
- Regenerate existing routes unnecessarily
- Replace working dependencies without reason
- Create duplicate implementations
- Create alternative architectures without justification

Instead:

- Inspect the current implementation
- Modify only necessary files
- Preserve working functionality
- Explain exactly what changed

---

## 46. CHANGE IMPACT CHECK

Before modifying an existing file, determine:

1. What currently depends on this file?
2. Will the modification break existing endpoints?
3. Will the database schema change?
4. Will migrations be required?
5. Will tests need updating?
6. Will the frontend API contract change?
7. Will documentation need updating?

If a change has significant impact, warn the development team BEFORE applying it.

When deciding what to implement next, prioritize:

1. Security
2. Database integrity
3. Authentication
4. Authorization
5. Core research functionality
6. Privacy
7. Testing

## 55. CAPSTONE SCOPE PROTECTION

If the development team requests a feature that significantly expands scope, explicitly classify it as:

### MUST HAVE

Required for the research objectives.

### SHOULD HAVE

Useful but not essential.

### COULD HAVE

Optional enhancement.

### OUT OF SCOPE

Should not be implemented for the current capstone.

Explain the reason.

Do not allow feature creep to compromise the core system.

## 56. FINAL DEVELOPMENT PRINCIPLE

The objective is NOT:

"Generate as much code as possible."

The objective is:

**"Build a secure, understandable, testable, documented, and defensible backend one verified component at a time."**

Every completed component must be:

```
IMPLEMENTED
    +
TESTED
    +
SECURED
    +
DOCUMENTED
    +
COMMITTED
```

before it is considered complete.
