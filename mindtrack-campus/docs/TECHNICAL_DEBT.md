# Technical Debt Log

This file tracks every intentional shortcut, simplification, or known limitation taken during backend development, per the project's development process (Section 50 of the Master Backend Prompt). Each entry is classified so that acceptable capstone simplifications are never confused with actual security issues — a security vulnerability is never logged here as "acceptable debt just because this is a capstone."

**Classification key:**
- **Acceptable Capstone Simplification** — a deliberate, low-risk scope reduction appropriate for a four-person undergraduate team; not expected to need resolution before submission.
- **Temporary Development Shortcut** — a stand-in solution expected to be replaced before deployment/UAT.
- **Known Limitation** — a real constraint of the current approach that is disclosed, not hidden, and does not currently pose a risk.
- **Security Issue** — must never be left unresolved; if anything below is ever reclassified into this category, it becomes the top development priority per Section 54.
- **Future Enhancement** — a nice-to-have improvement, not required for MVP.

## Notes on Maintaining This File

- When a new shortcut is taken, add a row **at the time the decision is made**, not retroactively at the end of a milestone — this matches the project's "do not hide technical debt" rule.
- If any item's risk level increases (e.g., TD-003 causes real UAT problems, or TD-006's gap actually lets a regression through), update its row rather than opening a duplicate entry.
- Milestone Reviews (see `docs/DEVELOPMENT_LOG.md`) should reference this file directly rather than re-deriving the list from memory.

| TD-010 | "Login" is listed in the Master Prompt's audit-log event list (Section 25), but the backend never observes an actual sign-in — Supabase Auth handles it directly, and the backend only ever verifies an already-issued token. Only `failed_authentication` was wired in Phase 20B. | Known Limitation | Capturing a true login event requires either a Supabase Auth Hook forwarding sign-in events to the backend, or a dedicated frontend-called endpoint right after sign-in — both are new surface area beyond wiring the existing `log_event()` helper. | Medium | Decide which approach to take (Auth Hook vs. dedicated endpoint) before Milestone 4 if a true login audit trail is required; not blocking current functionality. |
| TD-011 | Audit log content-safety ("do not store journal contents, passwords, or tokens") is enforced only by calling-convention discipline at each `log_event()` call site, not by any structural guarantee in the model or repository. | Known Limitation | `description` and `event_metadata` are free text/JSON by necessity, since audit events are heterogeneous; there is no practical way to structurally block arbitrary sensitive content from being passed in. | Medium | Have a second person review each of the 6 wired `log_event()` call sites (Phase 20B) specifically for this before Milestone 4's security testing phase. |
| TD-012 | `app/core/config.py` previously hardcoded real Supabase DB credentials, anon key, and the Fernet journal-encryption key as Python source defaults. The defaults were removed (fields are now required, no default), but the original values remain in git history from prior commits. | Known Limitation, partially resolved | Removing a value from the current file does not remove it from git history. | High until rotated | Rotate the Supabase DB password and generate a new Fernet key (re-encrypting any journal/check-in content already stored under the old key) before this repository is ever made public or shared beyond the 4-person team; confirm rotation status explicitly rather than assuming it's done. |
| TD-013 | `PrivacySettings.allow_activity_tracking` and `.anonymize_activity` are fully stored and API-editable (Phase 15), but no backend feature currently reads either flag to change any behavior — there is no aggregate/admin-facing view that would need to hide names/dates, and no data-collection path gated on tracking consent. | Known Limitation | These settings were built ahead of the features that would consume them (an admin/counselor dashboard was never in scope for Milestone 3). | Medium | Before claiming "Allow Activity Tracking works" or "Anonymize My Activity works" as done, build (or confirm out of scope for this capstone) whatever consuming feature is meant to honor these flags. |
